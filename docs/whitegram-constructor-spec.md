# ТЗ: Конструктор Whitegram (единый центр кастомизации интерфейса)

**Проект:** Whitegram Desktop
**Версия ТЗ:** 1.0
**Статус:** на реализацию
**Роль:** разработчик клиентского кода (C++/Qt, телеграм-десктоп кодовая база)

---

## 1. Суть задачи

Сейчас настройки внешнего вида и поведения клиента разбросаны по нескольким местам:
стандартные Настройки Telegram, отдельные секции Whitegram/AyuGram
(`ayu/ui/settings/`), отдельные боксы (шрифты, темы, архивы, фильтры).
Пользователь не видит всей картины и не понимает, что вообще можно настроить.

Нужен **Конструктор Whitegram** — единый центр кастомизации, в котором можно
настроить всё, что вообще настраивается в клиенте: тему и цвета, шрифты,
чаты и сообщения, списки чатов и фильтры, архивы, профиль, боковое меню,
контекстные меню, уведомления, звук, иконку приложения и т.д.

**Формат:** отдельный раздел настроек «Конструктор» с подразделами по зонам
интерфейса + живой предпросмотр изменений. Все настройки применяются сразу
(без перезапуска, где это технически возможно) и сохраняются локально.

---

## 2. Что уже есть (опора, а не пустое место)

Реализацию нужно строить поверх существующей инфраструктуры — не изобретать
параллельную:

| Что | Где |

| Палитра/цвета, квантизатор | `ayu/ui/utils/palette.cpp`, `color_cut_quantizer.cpp` |
| Выбор темы | `ayu/ui/boxes/theme_selector_box.cpp` |
| Выбор шрифта | `ayu/ui/boxes/font_selector.cpp` |

## 3. Структура Конструктора

Раздел «Конструктор» в главных настройках Whitegram. Внутри — подразделы:

1. **Тема и оформление** — темы, светлая/тёмная, акцентный цвет, палитра,
   фоны чата, стеклянный эффект (вкл/выкл, интенсивность).
2. **Шрифты и масштаб** — основной шрифт, моноширинный, размер, межстрочный
   интервал, масштаб интерфейса.
3. **Чаты и сообщения** — хвосты сообщений, аватары в чате, углы аватаров,
   поле ввода, счётчики, реакции, поведение контекстного меню.
4. **Список чатов** — фильтры/папки, скрытие счётчиков, «Все чаты»,
   компактность, вид архивов, кастомные архивы.
5. **Профиль** — кастомный фон профиля (зоны, видео-фон), видимость
   статусов/значков, отображение ID.
6. **Боковое меню и общий каркас** — элементы главного меню, переключатели
   ghost/стример в меню, музыкальный остров.
7. **Уведомления и звук** — значок на иконке, звук, всплывающие, тон,
   формат в трее.
8. **Иконка и запуск** — иконка приложения, анимация запуска, трей.
9. **Пресеты** — сохранение/загрузка/экспорт всей конфигурации (см. п. 5).

Точный состав полей каждого подраздела разработчик согласует на этапе
ревизи (этап 0) — там, где опция уже существует, переносим её как есть;
где не существует — создаём по образцу соседних.

## 4. Требования к реализации

### 4.1. UX
- Каждый подраздел — заголовок, логические блоки с подписями, опции.
  Использовать существующие `addSubsectionTitle` / `AyuBuilder` — стиль
  уже выработан, новый не нужен.
- **Живой предпросмотр**: изменения цвета/шрифта/углов применяются к
  интерфейсу сразу. Если мгновенное применение для какой-то опции
  невозможно (напр. иконка приложения, анимация запуска) — честная
  подпись «применится после перезапуска».
- Поиск по настройкам: строка поиска фильтрует опции по названию
  (по образцу `settings/settings_search.cpp`).
- Кнопка «Сбросить раздел» и «Сбросить всё» с подтверждением.

### 4.2. Технические
- Все новые значения — в `AyuSettings` (JSON-схема, как у существующих
  полей: сериализация `to_json/from_json`, значения по умолчанию,
  обратная совместимость при чтении старых конфигов — старый файл без
  новых полей обязан открываться без ошибок).
- Никаких глобальных синглтонов и записей «вразнобой»: изменение
  проходит через `AyuSettings`, UI слушает изменения (rpl/сигналы),
  как сделано у текущих фич.
- Ночные/тёмные темы: все новые цвета берутся из палитры, никаких
  «запечённых» `QColor`-значений в коде отрисовки (известный класс багов
  вида: цвет сохранился светлым при переключении темы на живую).
- Код в стиле проекта: clang-format, `.clang-tidy`, нейминг по соседним
  файлам, includes по алфавиту.
- CMake: новые файлы добавить в сборку (`Telegram/CMakeLists.txt` / cmake-модули),
  проверить сборку Release Win.

### 4.3. Границы возможного (честность Конструктора)
Всё, что клиент может менять локально, — настраиваемо. Серверные вещи
менять нельзя, и Конструктор не должен изображать, что может:
- нельзя: данные аккаунта, облачные настройки Telegram, чужие профили,
  содержимое сообщений, серверные лимиты;
- можно: всё локальное — отрисовка, раскладка, видимость локальных
  элементов, звуки, кэшируемые медиа-правила.
Если опция технически невозможна — она не появляется в UI, вместо
«серой» заглушки.

## 5. Пресеты (обязательная часть)

- **Сохранить текущую конфигурацию** в файл пресета (имя, дата, миниатюра
  темы, набор палитры).
- **Загрузить пресет** с предпросмотром «до/после» (ключевые цвета).
- **Экспорт/импорт** файла пресета (`*.wgtheme` / JSON) — возможность
  делиться настройками.
- Пресет хранит: значения из Конструктора + привязку к теме; не хранит
  аккаунт-специфичные данные (архивы с пин-хэшами, фоновые пути с
  локальными файлами — либо относительные пути, либо пропуск с
  предупреждением).
- Встроенные пресеты «из коробки»: минимум 3–5 (например: «Сток»,
  «Minimal», «Dark Glass», «Compact»).

## 6. План работ (этапы, каждый — отдельный PR)

| Этап | Что | Результат |
|---|---|---|
| 0. Ревизия | Пройти все `settings_*` секции и фичи `ayu/features/*`, составить полную карту «опция → где живёт → есть ли пробелы». Согласовать финальный состав подразделов | Карта опций, обновлённый состав разделов |
| 1. Каркас | Точка входа «Конструктор», навигация по подразделам, поиск, скелет всех разделов | Навигационно работающий пустой каркас |
| 2. Перенос настроек | По одному подразделу за PR: тема/шрифты → чаты → список чатов → профиль → меню → уведомления → иконка. Существующие опции переезжают в Конструктор, старые места либо ссылаются туда, либо остаются (решение согласовать на этапе 0) | Все существующие опции доступны из Конструктора |
| 3. Пробелы | Новые опции из карты этапа 0 там, где настройки не было | Полное покрытие |
| 4. Пресеты | Сохранение/загрузка/экспорт/импорт, встроенные пресеты | Работающие пресеты |
| 5. Полировка | Живой предпросмотр везде, где возможен; сбросы; подписи «после перезапуска»; аккуратные подписи на всех языках проекта (смотреть `lang`/`ayu_lang`) | Финальный вид |

Порядок этапов 2–5 можно слегка менять, но этап 0 обязателен до первого
строки кода каркаса.

## 7. Критерии приёмки

- [ ] «Конструктор» открывается из настроек Whitegram, все подразделы
      из п. 3 на месте и не пустые.
- [ ] Каждая опция, существовавшая раньше, доступна из Конструктора
      и работает как раньше.
- [ ] Поиск находит опцию по названию (rus/eng строки проекта).
- [ ] Изменение темы/цвета/шрифта/углов видно без перезапуска; смена
      иконки приложения и анимации запуска честно помечены
      «после перезапуска».
- [ ] Тёмная тема: переключение день/ночь при открытом Конструкторе
      не оставляет светлых артефактов (проверить боксы и превью).
- [ ] Пресет сохраняется, перезагружается, экспортируется и
      импортируется; старый конфиг без новых полей открывается чисто.
- [ ] Сброс раздела и сброс всего работают с подтверждением.
- [ ] Сборка Release (Win) проходит, clang-format/tidy чистые.
- [ ] Ничего из «серверного» (п. 4.3) в UI не заявлено.

---

## 8. Не входит в задачу (out of scope)

- macOS/Linux-специфика (только Windows-проверка; код, конечно,
  платформонейтральный, где возможно).
- Плагины/скриптовый API для Конструктора.
- Онлайн-библиотека пресетов (только локальные + файл-обмен).
- Новые переводчики строк — использовать существующую систему
  локализации проекта.

---

## 9. Риски и открытые вопросы

1. **Конфликт с апстримом** — AyuGram периодически обновляется; менять
   существующие файлы секций нужно минимально, новые экраны — в новых
   файлах, чтобы мерж не болел.
2. **Живое применение** — часть настроек в tdesktop применяется через
   пересоздание виджетов; определить на этапе 0, какие опции реально
   live-appliable, и не выдавать желаемое за возможное.
3. **Локализация** — новые строки добавить по принятому в проекте
   процессу (`ayu_lang`); на время разработки допустимы англ. строки,
   финал — только через систему локализации.
4. **Состав опций** — финальный чек-лист утверждается после этапа 0
   ревизии; это ТЗ фиксирует рамки, а не исчерпывающий список полей.
